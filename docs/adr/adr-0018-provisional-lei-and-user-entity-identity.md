## Status

Accepted

## Context

Axiom maintains a master list of Legal Entity Identifiers (LEIs) sourced from GLEIF.
As the product moves toward permissioned access for clients, counterparties, and internal
users, two interrelated gaps must be addressed:

1. **Not every entity has an official GLEIF LEI.** Clients, counterparties, and internal
   entities that pre-date or fall outside the mandatory LEI regime cannot be linked to an
   official identifier. Without a workaround, these entities cannot participate in the
   Axiom permission model at all.

2. **Users need an entity identity.** Permissions in Axiom must be scoped to a legal
   entity (or group of entities in a parent–child hierarchy), not just to a global role.
   Without a user–entity link the coarse `admin` / `user` model from
   [ADR-0010](adr-0010-user-auth-registration-system.md) cannot be extended to
   entity-scoped access control.

## Decision Drivers

- **DRV-001**: The GLEIF LEI standard (ISO 17442) provides a structured, globally unique
  20-character identifier that Axiom already stores and queries at scale.
- **DRV-002**: Acting as a lightweight provisional LEI issuer — following the same
  succession policy as GLEIF — lets Axiom capture and link entities today even when no
  official LEI exists, and provides a smooth upgrade path when one is later issued.
- **DRV-003**: The Level 2 relationship data already present in Axiom records parent–child
  entity hierarchies; permissions should be optionally inherited down that hierarchy.
- **DRV-004**: Any change must be additive and backwards-compatible; existing LEI search,
  import pipelines, and audit trails must be unaffected.
- **DRV-005**: The provisional LEI prefix must be clearly distinguishable from official
  GLEIF codes to avoid confusion in downstream systems.

## Decision

### 1. Provisional LEI Records

Extend `lei_raw.lei_records` with two new columns:

| Column | Type | Purpose |
| ------ | ---- | ------- |
| `is_provisional` | `BOOLEAN NOT NULL DEFAULT FALSE` | Marks records that are Axiom-issued rather than GLEIF-sourced |
| `provisioning_source` | `VARCHAR(1000)` | Free-text label or URL identifying why the provisional LEI was created (e.g. `onboarding`, `counterparty`, `internal`, or document URL) |

No separate table is created. Keeping provisional records in the same table means all
existing search, filter, and sort paths continue to work unmodified. The `is_provisional`
flag allows callers to distinguish origins.

### 2. Provisional LEI Identifier Format

Provisional LEIs use the same ISO 17442 structure (18 alphanumeric chars + 2 check digits):

```text
AXIO <14 alphanumeric body> <2 ISO-17442 check digits>
```

- **Prefix**: `AXIO` — clearly identifies Axiom as the issuing body.
- **Body**: 14 random uppercase alphanumeric characters generated by the service at
  creation time.
- **Check digits**: calculated using the standard ISO 7064 MOD 97-10 algorithm so the
  code passes any standard LEI format validator.

The prefix `AXIO` does not correspond to any registered GLEIF LOU; GLEIF-issued LEIs
will never carry this prefix, guaranteeing namespace separation.

### 3. Succession Policy

When a provisional LEI entity later receives an official GLEIF LEI, an admin triggers a
succession operation:

1. The official LEI record is confirmed to exist in `lei_raw.lei_records` (either already
   present from GLEIF ingestion or importable on demand).
2. The provisional record's `successor_lei` column is set to the official LEI code.
3. The provisional record's `entity_status` is set to `MERGED`.
4. Existing `user_entity_links` rows continue to reference the provisional LEI; the
   existing `exactLEIMatchWhereClause` in the repository already follows `successor_lei`
   chains so all lookups transparently resolve to the official entity.

This mirrors the GLEIF-defined succession policy and requires no migration of
`user_entity_links` rows.

### 4. User–Entity Identity Links

A new table `user_entity_links` records the relationship between a system user and one
or more LEI entities:

| Column | Type | Notes |
| ------ | ---- | ----- |
| `id` | `UUID PK` | Surrogate key |
| `user_id` | `UUID FK → users.id` | The linked user |
| `lei` | `VARCHAR(20)` | LEI code (official or provisional) |
| `entity_role` | `VARCHAR(50)` | Role scoped to this entity (e.g. `viewer`, `trader`, `entity_admin`) |
| `include_children` | `BOOLEAN` | Whether permissions cascade down Level 2 children |
| `granted_by` | `UUID FK → users.id` | Admin who created the link |
| `granted_at` | `TIMESTAMPTZ` | When the link was created |
| `expires_at` | `TIMESTAMPTZ NULL` | Optional expiry; NULL = no expiry |
| `revoked_at` | `TIMESTAMPTZ NULL` | Soft-revoke; NULL = active |
| `notes` | `TEXT NULL` | Optional admin notes |
| `created_at` / `updated_at` | `TIMESTAMPTZ` | Standard audit timestamps |

A unique index on `(user_id, lei)` prevents duplicate links.

### 5. RBAC Groundwork

The `entity_role` column in `user_entity_links` introduces entity-scoped roles distinct
from the global `role` column on `users`. The initial set of entity roles is:

| Role | Meaning |
| ---- | ------- |
| `viewer` | Read-only access to this entity's data |
| `trader` | Read + trade instruction access |
| `entity_admin` | Can manage other users' links to this entity |

This is intentionally simple. A full RBAC model (groups, fine-grained permissions,
permission inheritance) is deferred to a follow-on ADR once access patterns from the
first rollout are understood.

### 6. Search Integration

Provisional LEI records sit in `lei_raw.lei_records` alongside official GLEIF records
and are therefore included in all existing search, filter, and sort operations
automatically. The `is_provisional` field is returned in API responses so the frontend
can display a visual badge distinguishing provisional from official records.

## Decision Outcome

**Chosen Option:** Extend `lei_raw.lei_records` in-place with provisional flags; use
`AXIO`-prefixed 20-character codes with valid ISO 17442 check digits; link users to
entities via a dedicated `user_entity_links` table.

## Consequences

### Positive

- **POS-001**: All existing GLEIF ingestion pipelines, search queries, and audit trails
  require no modification.
- **POS-002**: The `successor_lei` mechanism already in the repository layer provides
  transparent succession from provisional to official LEI without migrating identity links.
- **POS-003**: The `is_provisional` flag makes provisional origin explicit in every API
  response, supporting clear UI differentiation.
- **POS-004**: Entity-scoped roles in `user_entity_links` form the foundation for
  future fine-grained RBAC without requiring a big-bang rewrite.
- **POS-005**: Client and counterparty onboarding can proceed immediately, even before an
  official LEI is issued.

### Negative

- **NEG-001**: Provisional LEI codes carry the `AXIO` prefix which is not a registered
  GLEIF LOU; downstream consumers that validate LOU prefixes will reject these codes.
  They must be treated as internal identifiers only.
- **NEG-002**: `user_entity_links` entity roles are not yet enforced at the API handler
  level; enforcement requires a future permission-checking middleware layer.
- **NEG-003**: The `include_children` flag requires Level 2 data to be populated for
  hierarchy traversal; where Level 2 data is incomplete the hierarchy is necessarily
  partial.

### Mitigation

- **MIT-001**: Document that `AXIO`-prefixed LEIs are Axiom-internal identifiers in all
  data dictionaries, API docs, and downstream integration guides.
- **MIT-002**: Plan a follow-on ADR for entity-scoped middleware enforcement once the
  first consumer use-cases are clear.
- **MIT-003**: Surface `include_children` warnings in the UI when Level 2 data coverage
  for the selected entity is low.

## Alternatives Considered

### Separate `provisional_lei_records` Table

- **Description**: Store provisional LEI records in a distinct table, separate from
  `lei_raw.lei_records`, with its own schema and validation rules.
- **Rejection Reason**: Would require duplicating or branching all search, filter, sort,
  and audit query paths. The `is_provisional` flag achieves clear differentiation with
  zero query duplication and no maintenance surface increase.

### External GLEIF Sandbox / Pre-LEI

- **Description**: Use GLEIF's own Pre-LEI (pre-validation LEI application) process to
  obtain codes for entities without a final LEI.
- **Rejection Reason**: Pre-LEI issuance requires a formal application to a Local
  Operating Unit (LOU), takes days to weeks, and costs money. This is incompatible with
  the need to onboard clients and counterparties immediately during a commercial workflow.

### Global Role Extension Only (No Entity Links)

- **Description**: Add entity-specific attributes directly to the `users` table
  (e.g. a `primary_lei` column) rather than a separate link table.
- **Rejection Reason**: Users legitimately need links to multiple entities. A single
  column cannot represent this; a link table is the correct relational design.

## Implementation Notes

- **IMP-001**: Provisional LEI code generation is implemented in
  `backend/internal/service/provisional_lei_service.go`. The ISO 7064 MOD 97-10 check
  digit calculation is self-contained in that file.
- **IMP-002**: Migration `000062` adds `is_provisional` and `provisioning_source` to
  `lei_raw.lei_records`. Existing rows default to `is_provisional = FALSE`.
- **IMP-002a**: Migration `000073` increases `provisioning_source` from `VARCHAR(50)` to
  `VARCHAR(1000)` to support long document URLs and extended references (e.g., prospectus
  links). This accommodates real-world provisioning sources including full URLs (typically
  100–500 characters) plus optional metadata.
- **IMP-003**: Migration `000063` creates `user_entity_links`.
- **IMP-004**: Admin endpoints for provisional LEI management are mounted under
  `/api/v1/lei/provisional` (JWT + AdminRequired).
- **IMP-005**: User–entity link management endpoints are mounted under
  `/api/v1/user-entity-links` (JWT + AdminRequired).
- **IMP-006**: The succession endpoint `POST /api/v1/lei/provisional/:lei/succeed` sets
  `successor_lei` on the provisional record, updates `entity_status` to `MERGED`, and
  writes an audit row.
